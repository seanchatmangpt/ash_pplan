## 1. Executive Profile & Lens

Andy Hunt and Dave Thomas authored *The Pragmatic Programmer: From Journeyman to Master*, establishing timeless engineering principles that guide resilient software design:
1. **DRY (Don't Repeat Yourself)**: Every piece of knowledge must have a single, unambiguous, authoritative representation within a system. Duplicating business rules across schemas, documentation, and code guarantees divergence and bugs.
2. **Orthogonality**: Components should be designed so that changes to one do not affect others. Persistence, workflow execution, planning algorithms, and business actions should vary independently.
3. **Tracer Bullets**: Build architecture with thin, end-to-end, runnable paths that touch every tier of the system immediately, verifying integration before fleshing out details.
4. **Ruthless Testing & Zero Broken Windows**: Never tolerate compiler warnings, flaky tests, or fake mocks that test assumptions rather than reality. Fix broken windows before they spread decay.

Evaluating `ash_pplan` through the Pragmatic Programmer lens means examining whether `ontology.ttl` truly serves as the single source of truth, whether layers are cleanly decoupled, whether release verification runs end-to-end tracer scripts, and whether testing enforces zero-mock discipline.

## 3. Architectural Analysis & Findings

### 3.1 DRY Law: Canonical Single Source of Truth (`ontology.ttl`)
In `ash_pplan`, the DRY principle is enforced at the ontological level:
```
             ┌─────────────────────────────────────────────────────────┐
             │                 ontology.ttl (Canonical)                │
             │     W3C P-PLAN / PROV-O Profile / st:RunStatusMachine   │
             └────────────────────────────┬────────────────────────────┘
                                          │
                   ┌──────────────────────┴──────────────────────┐
                   │ bin/manufacture (ggen_igniter SPARQL sync)  │
                   └──────────────────────┬──────────────────────┘
                                          ▼
     ┌─────────────────────────────────────────────────────────────────────────┐
     │ Manufactured Elixir Projections (DO NOT EDIT)                           │
     │ - lib/ash_pplan/catalog/     (Runtime projection catalog)               │
     │ - lib/ash_pplan/workflow/    (P-PLAN process definitions)               │
     │ - lib/ash_pplan/reactor/durable/status.ex (Guarded status FSM)          │
     └─────────────────────────────────────────────────────────────────────────┘
```
- **Single Source of Authority**: All domain concepts, projection mappings, status machines, and capability standings originate in `ontology.ttl`.
- **Prohibition of Manual Edits**: Generated files explicitly declare their lineage:
  ```elixir
  # lib/ash_pplan/reactor/durable/status.ex:1-6
  # GENERATED by ggen_igniter from ontology.ttl (st:RunStatusMachine rows).
  # Do not edit. Regenerate:
  #   mix ggen_igniter.sync --pack-dir priv/ggen/ash-pplan-workflow-pack ...
  ```
  Manual modifications to generated files are strictly prohibited by repo doctrine. If a change is needed, engineers modify `ontology.ttl` or SPARQL templates and rerun `./bin/manufacture`.
- **Zero Drift via Git Status**: The release pipeline enforces that after running `./bin/manufacture`, `git status --porcelain` must be clean, ensuring that generated code never drifts from the ontology.

### 3.2 System Orthogonality
The architecture exhibits exceptional orthogonality:
1. **Storage vs Execution**: `AshPPlan.Reactor.Durable.Store` is an interchangeable behaviour. Swapping from in-memory `Store.Ets` to disk-backed `Store.Dets` requires zero modifications to `Reactor` plans or `Engine` logic.
2. **Planning vs Actuation**: Hierarchical planning (`AshPPlan.HTN`) and policy checking (`AshPPlan.FOND`) are purely declarative computation modules. They produce plans carrying `authority: :none` or `:construct`. Actuation (`DO`) is isolated to `AshPPlan.Action.Run`. Changing a planning heuristic does not affect action execution or database policies.
3. **Ontology vs Runtime**: The P-PLAN ontology is technology-neutral. It defines the abstract execution graph without coupling itself to Elixir ASTs or BEAM bytecode.

### 3.3 Tracer Bullets in Release Engineering
The Pragmatic Programmer advocates building automated tracer paths. `ash_pplan` provides executable tracer scripts in `./bin/`:
- `./bin/conform`: Validates that `ontology.ttl` satisfies all SHACL constraints in `ontology/shapes.ttl`.
- `./bin/conform-falsify`: Injects deliberate counterexamples and proves that the SHACL gate fails closed. A gate that cannot refuse is vacuous.
- `./bin/manufacture`: Runs the full SPARQL-driven code generation pipeline end-to-end.
- `./bin/verify-package`: Verifies that the published package builds and compiles in an isolated environment.
- `./bin/receipt`: Generates an admitted cryptographic release receipt bound to the release commit HEAD.

### 3.4 Zero Broken Windows & Zero-Mock Discipline
The codebase adheres to a strict "no broken windows" policy:
- **Zero Compiler Warnings**: Enforced by `mix compile --warnings-as-errors`.
- **Zero Formatting Drift**: Enforced by `mix format --check-formatted`.
- **Chicago-School Zero-Mock Discipline**: In `test/ash_pplan_mock_discipline_test.exs`, an automated AST scanner inspects every file in `lib/` and `test/` against the fleet mock-discipline regex:
  ```elixir
  @regex ~S[(use|import) +(Mox|Mimic|Patch)\b|(Mox|Mimic|Patch)\.|:meck\.|mockall|MagicMock]
  ```
  The scanner fails closed if any mock framework is introduced. Tests interact with real BEAM processes, real ETS tables, and real DETS storage, ensuring that tests prove actual system behavior rather than unverified developer assumptions.

## 4. Probing Inquiries & Falsifiers

### Inquiry 1: What prevents an engineer from bypassing the ontology and manually editing generated code?
**Analysis**: The release gate executes `./bin/manufacture` followed by `git diff --exit-code`. If any manufactured file has been hand-edited, the regeneration overwrites the edit, producing an uncommitted diff that immediately aborts the release pipeline.
**Falsifier**: Proved by Release Gate 8 in `AGENTS.md`.

### Inquiry 2: Are SHACL conformance gates capable of refusing invalid ontology changes?
**Analysis**: `./bin/conform-falsify` tests 25+ invalid mutations (such as duplicate projection orders, non-IRI source terms, and invalid standing values) against `ontology/shapes.ttl`, confirming that each mutation is refused with a nonzero exit code.
**Falsifier**: Proved by `./bin/conform-falsify` exiting with 0 (confirming all falsifiers were caught).

### Inquiry 3: Does zero-mock discipline make tests excessively slow or flaky?
**Analysis**: Because the BEAM creates lightweight isolated processes in microseconds and in-memory ETS tables run at RAM speeds, real-process integration tests execute in seconds without flakiness or external mock servers.

## 6. Verdict & Operational Recommendations

### Verdict: **APPROVED**
`ash_pplan` v26.11.10 is an architectural tour de force from the Pragmatic Programmer perspective. It eliminates duplicated knowledge by anchoring the system in a canonical ontology, protects orthogonality through formal interfaces, verifies everything with automated tracer bullets, and eliminates broken windows through zero-mock discipline.

### Operational Recommendations
1. **Automated Diff-Checking in CI**: Ensure that every pull request in CI runs `./bin/manufacture` followed by `git diff --exit-code` to catch any attempted manual edits to manufactured files before merge.
2. **One-Command Developer Onboarding**: Maintain a consolidated `bin/verify-all` script that chains `bin/conform`, `bin/manufacture`, and `mix test` to provide a single tracer command for new contributors.
