# Order-to-Cash Case Study

See also: `docs/case-studies/receipts/o2c-run-20261004T030106Z.json` · `test/workflow/canonical_court_test.exs` · `bench/BASELINES-CANONICAL.md` · `bench/fleet/logs/fleet_soak_w16.log`

## Situation

Order-to-cash (O2C) is the canonical Celonis-style process-mining case study: an order
flows `admit_order -> authorize_payment -> human_release -> commit_shipment`, and the
questions are exactly the ones Celonis answers with mined event logs — is every case
complete, is execution exactly-once, does conformance detect the violations, and can a
third party replay the evidence.

In ash_pplan the O2C spine is not a slide — it is the canonical example court. The
durable spine `qualified_fulfillment_durable_spine` (4 tasks carved out of the 11-task
`qualified_fulfillment` workflow generated from `ontology.ttl`) is executed for real on
the durable engine, on real ETS/DETS stores, and its ledger is exported as OCEL 2.0
evidence that the real `ex4pm` conformance engine admits.

This is the mining evidence Celonis would start from — except here it was not mined

per standing checkpoint, ordered by the ledger `seq`.

## Actions

What the engine does about the weaknesses mining finds (all asserted in
`test/workflow/canonical_court_test.exs`):

- **Exactly-once under crash**: a genuinely killed attempt (`Process.exit(..., :kill)`
  with a dead claim) is taken over after the lease lapses; effects stay exactly-once
  (`admit=1 authorize=1 commit=1` after takeover).
- **Tamper evidence**: the chained digest changes the moment the ledger changes — a
  `claim_undo/4` write into a parked run's ledger flips the digest, detected.
- **Standing admission**: `Standing.receipt/2` over the run's own events yields an
  ALIVE receipt at ceiling `CONSTRUCT` (grant `NONE`); a reordered ledger (commit
  before its dependency) is refused with a typed broken term, and a false world check
  is refused `R_missing_consequence`.
- **Compensation law**: a failing commit lands the run `:failed` terminal; steps
  without `undo/4` stay standing (carried forward, not reversed); a clean retry run
  re-executes only the failed step.

## Limitations

- **No wall-clock event timestamps**: checkpoint rows carry no wall-clock timestamps,
  so OCEL event timestamps reflect export time; the ledger `seq` is the authoritative
  order (`docs/architecture.md`, "Process evidence export (OCEL 2.0)"). The run
  receipt carries a single `executed_at` for the whole run, not per-event times. No
  case-duration or SoD-timing analysis is possible on this log; only ordering-based
  conformance.
- **Single-subject identity fields are fixtures**: the receipt's `subject_sha`
  (`sha256:1111...`), `base_sha` (`sha256:2222...`) and subject
  (`sha256:abab...`) are test fixtures, not real commit digests.
- **Soak caveats**: the 507-cycle log was terminated by hand at cycle 507 (not
  deadline-completed), so it has no `Finished in` summary line; the first soak run of
  this wave hit a real edge at cycle 178 — a kill landing before the writer's first
  ack leaves zero acked runs and trips `verify_acked` ("writer acked nothing",
  `bench/fleet/logs/fleet_soak_w16.log` was overwritten by the rerun; the failure is
  reproducible via the same command) — an honest falsifier the harness surfaced.
- **Machine load not controlled** for the bench rows (see caveats above); treat bench
  cells as bands, not tight medians.
- **Conformance numbers are measured in the ex4pm repo** (`/Users/sac/ex4pm`, HEAD
  `9f7aecd`), on its fixture OCEL log, not on ash_pplan's exported run — the
  ash_pplan export is admitted through the ex4pm pipeline (ingest/parse/validate all
  `1` per soak cycle), but the 5-dimensional conformance vector itself is ex4pm's
  fixture measurement.
